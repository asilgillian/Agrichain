
1. New Core Module: Commodity Management
This should sit as a cross-cutting master data module (like “Streams” or “Admin Units”).
1.1 Commodity Master
Defines what is being traded
Table: Commodity
•	CommodityID
•	Name (e.g. Coffee)
•	ScientificName
•	DefaultUnit (kg, bags, tonnes)
•	IsActive

1.2 Commodity Type (Variant Layer)
This is where our real operations live
Table: CommodityType
•	CommodityTypeID
•	CommodityID (FK)
•	Name (e.g. Robusta Cherry, Arabica Parchment, Green Bean)
•	Stage (Raw / Intermediate / Finished)
•	ParentCommodityTypeID (for transformations)
•	IsTradable (yes/no)
•	DefaultMoistureRange
•	DefaultQualityParameters (JSON or linked table)
👉 Example hierarchy:
•	Coffee
o	Robusta Cherry (RAW)
o	Robusta Parchment (INTERMEDIATE)
o	Robusta Green Bean (FINISHED)

1.3 Commodity Parameters (Dynamic Config Layer)
A. Seasonal Parameters
Table: CommoditySeason
•	SeasonID
•	CommodityTypeID
•	SeasonName (e.g. 2026 Main Crop)
•	StartDate / EndDate
•	Region (optional)
•	IsActive

B. Daily Pricing
Table: CommodityPrice
•	PriceID
•	CommodityTypeID
•	Date
•	PricePerKg
•	Currency
•	Source (manual / market / contract)
•	Region (optional)
👉 This replaces hardcoding price logic in procurement

C. Conversion Ratios
Table: CommodityConversion
•	ConversionID
•	FromCommodityTypeID
•	ToCommodityTypeID
•	ConversionRate (e.g. 0.22)
•	ProcessType (Pulping, Drying, Hulling)
•	MinRate / MaxRate
•	EffectiveDate
•	Version
👉 Example:
•	Cherry → Parchment = 0.45
•	Parchment → Green Bean = 0.50
•	Cherry → Green Bean = 0.22

D. Quality Parameters per Commodity Type
Table: CommodityQualitySpec
•	SpecID
•	CommodityTypeID
•	ParameterName (Moisture, Defects, Screen Size)
•	MinValue / MaxValue
•	Unit
•	AffectsPrice (yes/no)

E. Processing Rules
Table: CommodityProcessFlow
•	FlowID
•	CommodityTypeID
•	AllowedNextStages
•	MandatoryProcesses
•	ExpectedOutturn %

2. Impact on Existing Modules (What You Need to Change)
Now the important part—how this plugs into our current system.

MODULE 2: Field Operations (Bulking)
Updates:
•	Replace “Crop Type” → CommodityType
•	When creating a batch:
o	Must be single CommodityType
•	Pre-processing deduction:
o	Replace static % with:
→ pull from CommodityConversion + ProcessType
New Logic:
•	System calculates expected output using conversion ratios
•	Warn if agronomist deviates beyond allowed range

MODULE 3: Buying Station
Truck Arrival & Offloading

Sampling & Quality

o	Dynamically loaded from CommodityQualitySpec
👉 No more hardcoding:
•	Coffee moisture rules
•	Defect thresholds

Pricing Decision
BIG CHANGE:

Manual base price entry
You now:
•	Pull Daily Commodity Price
•	Apply:
o	Quality adjustments
o	Contract floor price
👉 Formula becomes:
Final Price = CommodityPrice ± QualityAdjustments ± Incentives - Deductions

4. Key Architecture Shift
Right now:
Flow is operational (farm → batch → lot)
After this:
Flow becomes commodity-driven
Everything keys off:
Commodity → CommodityType → Process → Conversion → Price

5. Example End-to-End Flow (With Our New Model)
1.	Farmer delivers:
o	Robusta Cherry
2.	Bulking:
o	Batch created (Cherry)
3.	Processing:
o	Cherry → Parchment (0.45)
o	Parchment → Green Bean (0.50)
4.	System computes:
o	Expected Green Bean yield = 0.22
5.	Pricing:
o	Pull Green Bean price/kg
o	Apply quality adjustments
6.	Payment:
o	Farmer paid based on equivalent value

6. Critical Design Decisions (Don’t Skip These)
1. Do you allow multi-commodity batches?
👉 Recommendation: NO (keep clean)

2. Do you fix conversion rates or allow ranges?
👉 Recommendation:
•	Store:
o	Expected
o	Min/Max tolerance

3. Do you price at raw or processed level?
👉 Two options:
•	A: Pay at cherry level (simpler)
•	B: Pay at equivalent green bean value (more accurate)
